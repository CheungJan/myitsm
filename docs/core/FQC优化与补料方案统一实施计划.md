# FQC 优化与补料方案统一实施计划

## 1. 方案概述

### 1.1 背景

FQC（最终质量检测）在生产工单完工后进行，涉及成品整机和 BOM 配件的逐件检测。当前模块分两线推进：

- **主线 A**（本次会话已完成）：单记录多判定 + 按行审核 + 更换按钮 + 仓库联动 + 反审核 + TMS04
- **支线 B**（待实现）：补料工作流（OV=8 草稿生成、工单提交约束、冗余量、退料、TMS04 扩展）

两者为上下游关系：主线 A 解决"判定时发生了什么"，支线 B 解决"判定后怎么处理不良品"。

### 1.2 应用场景分类

本方案主要针对**生产工单关联的 FQC**，但需考虑其他质检场景的处理策略：

| 场景 | 来源单据 | 补料要求 | 更换要求 | 说明 |
|------|---------|---------|---------|------|
| **生产工单 FQC** | 生产工单 | 需要补料 | 需要更换 | 本次方案重点，保证生产任务 |
| **单独质检** | 入库单/无来源 | 不需要补料 | 不需要更换 | 只记录物料状态，不做强制处理 |
| **过程检测** | 生产工单 | 需要补料 | 需要更换 | 类似 FQC，保证生产任务（待扩展） |

**场景说明**：
1. **单独质检**：无生产工单关联的质检（如来料检验），仅记录物料合格/不合格状态，不触发补料和更换流程
2. **过程检测**：生产过程中的中间检测，发现不良品需要补料和更换以保证生产任务，处理逻辑与 FQC 一致（待后续扩展）

### 1.3 核心流程

```
工单 QC_PENDING
  │
  ├─ 录入页加载 BOM（成品的物料清单）
  ├─ 逐行判定（成品 + 配件 + 耗材）
  ├─ 【申请补料】按钮 → 生成 OV=8 草稿
  │
  ├─ 提交 → 生成 batch_id + 单子记录（含所有行）
  │
  ├─ 审核
  │   ├─ 通过（各行按 `_rqc(row)` 分流）
  │   │   ├─ GA → IV=8 入成品仓
  │   │   ├─ BF → IV=11 报废暂存 → OV=7 报废出库
  │   │   ├─ BH → IV=11 返修暂存 → OV=9 返修出库
  │   │   ├─ TH → IV=11 退换暂存
  │   │   └─ 非合格品 → OV=8 补料出库 + TMS04 写入
  │   └─ 退回 → auditflg='8'，不触发仓库联动
  │
  ├─ 反审核 → 作废下游草稿 + 回退工单状态
  │
  └─ 作废 → auditflg='V'
```

### 1.4 工单取消流程

任何中间态均可取消工单，系统自动清理关联单据：

```
工单取消 (transition → CANCELLED)
  │
  ├─ 检查下游已审核单据
  │   ├─ QC 已审核 (auditflg='1')        → ❌ 阻止，需先反审核QC
  │   └─ 下游 IV/OV 已审核 (auditflg='2') → ❌ 阻止，需先反审核
  │
  └─ 清理
      ├─ OV=8 草稿 (auditflg='0')        → 作废 (→ 'V')
      ├─ OV=8 已审核 (auditflg='2')      → 查明细 → 生成 IV=3 退货草稿 + TMS04退料(consume_type='5')
      │                                      └─ 仓库人工审核后退回库存
      ├─ QC 草稿/退回 (auditflg∈{0,8})    → 作废 (→ 'V') + 作废下游 IV/OV 草稿
      └─ 工单                               → CANCELLED
```

各状态取消行为：

| 当前状态 | 已发生操作 | 取消时处理 |
|---------|-----------|----------|
| DRAFT | 仅工单 | 前端直接 DELETE |
| RELEASED | OV=8 草稿 | 作废 OV=8 草稿 |
| PICKING | OV=8 草稿待审核 | 同上 |
| IN_PROGRESS | OV=8 已审核领料 | 作废草稿 + 已审OV=8生成IV=3退货 |
| QC_PENDING | +FQC质检草稿 | 上述 + QC草稿作废 + 下游IV/OV草稿作废 |
| COMPLETED | 全部走完 | 不允许取消 |

## 3. 补料方案详细设计

### 3.1 核心原则

**三个动作分离**，而不是把补料塞进审核流程：

| 动作 | 触发 | 状态 | 说明 |
|------|------|------|------|
| **判定**（已实现） | FQC 录入 → 提交 | auditflg='0' | 按行判定，无需等补料 |
| **申请补料**（已实现） | 申请补料按钮 → 生成 OV=8 草稿 | OV.auditflg='0' | OV=8 审核完成后再提交 QC |
| **更换记录**（已实现） | 工单更换按钮 → 记录过程记录表 | tms05_replace_record | EID物料/eid+EID状态更新；批次物料/batch_no+FQC后回写EID |

### 3.2 完整流程

#### 场景：检测发现配件 BF，需要补料

```
FQC 录入页
  ├─ 成品 TS01 → GA
  ├─ 配件 BS4201 → BF  ← 点击【申请补料】
  │    └─ 调用 POST /qc/batches/<id>/replenish（新 API）
  │         └─ 生成 OV=8 草稿（auditflg='0'）
  │
  ├─ 点击【提交】→ 生成 QC 草稿（auditflg='0'）
  │
仓库
  └─ 审核 OV=8 补料出库 → 完成领料

工单页
  ├─ 点击【更换】按钮
  ├─ EID物料：选择旧/新 EID → 更新EID状态表
  ├─ 批次物料：选择旧/新批次号 → FQC合格后回写EID
  └─ 记录到 tms05_replace_record 表

FQC 结果页 / 录入页
  └─ 审核 QC → 仓库联动（跳过已补料行）
```

#### 状态流转

```
┌─────────────────────────────────────────────────┐
│ FQC 录入                                        │
│ 判定完毕 → 点击【申请补料】                      │
│   → 后端 POST /qc/batches/<id>/replenish         │
│       ├─ 生成 OV=8 草稿（auditflg='0'）          │
│       ├─ 记录 replenish_status = 'pending'       │
│       └─ 返回 OV 单号                            │
│                                                 │
│ 仓库审核 OV=8                                   │
│   → replenish_status = 'completed'              │
│   → 出库领用材料                                │
│                                                 │
│ 工单页 → 点击【更换】按钮                        │
│   → EID物料：选EID + 更新EID状态表               │
│   → 批次物料：选批次号（FQC后回写EID）            │
│   → 记录到 tms05_replace_record 表               │
│       ├─ old_batch_no / new_batch_no（批次）    │
│       ├─ old_eid / new_eid（EID）               │
│       └─ replace_date（更换时间）                │
│                                                 │
│ FQC 提交                                        │
│   → 检查 replenish_status                       │
│       ├─ 'completed' → 正常提交                  │
│       └─ 'pending'  → 可选强制提交（草稿）        │
│                                                 │
│ FQC 审核                                        │
│   → 跳过已补料的行（不重复生成 OV=8）              │
└─────────────────────────────────────────────────┘
```

### 3.3 关键数据结构

#### 3.3.1 BOM 冗余量

```sql
ALTER TABLE tmm41_bom ADD COLUMN redundancy_ratio NUMERIC(5,4) DEFAULT 0 
  COMMENT '补料冗余比例：0=不冗余，0.1=10%，1=100%';
```

**用途**：BOM 上配件维度的冗余量，控制一次补料生成时的批量数量，减少多次补料操作。

**计算公式**：`补料数量 = SUM(非合格行数量) × (1 + redundancy_ratio)`

**例子**：某配件 BF 了 5 个，`redundancy_ratio=0.2`，则 OV=8 生成 6 个。

#### 3.3.2 补料状态字段

方案 A：QC 记录级别

```sql
ALTER TABLE tqc10_result ADD COLUMN replenish_status VARCHAR(10) DEFAULT ''
  COMMENT '补料状态：''''=无补料 pending=待补料 completed=已补料';
ALTER TABLE tqc10_result ADD COLUMN replenish_ov_billid VARCHAR(12) DEFAULT ''
  COMMENT '补料出库单号';
```

方案 B：行级别（更精细，推荐）

```sql
ALTER TABLE tqc11_resultdt ADD COLUMN replenish_status VARCHAR(10) DEFAULT ''
  COMMENT '行级补料状态';
ALTER TABLE tqc11_resultdt ADD COLUMN replenish_ov_billid VARCHAR(12) DEFAULT '';
ALTER TABLE tqc11_resulteid ADD COLUMN replenish_status VARCHAR(10) DEFAULT '';
ALTER TABLE tqc11_resulteid ADD COLUMN replenish_ov_billid VARCHAR(12) DEFAULT '';
```

**推荐方案 B**：因为同一批次中不同物料可能有不同的补料进度。

#### 3.3.3 物料消耗统计扩展

**TMS04 字段状态**：

| 字段 | 类型 | 状态 | 说明 |
|------|------|------|------|
| consume_type | VARCHAR(2) | ✅ 已实现 | 消耗类型：1定额 2补料 3报废 4返修 5退料入库 |
| ref_bill_type | VARCHAR(2) | ✅ 已实现 | 来源单据类型：OV/IV |
| ref_bill_id | VARCHAR(20) | ✅ 已实现 | 关联单据号 |
| qty | DECIMAL | ✅ 已实现 | 数量 |
| cost | DECIMAL | ✅ 已实现 | 成本（数量 × 标准价格） |

**统计场景**：
- 定额领料：consume_type='1', ref_bill_type='OV', ref_bill_id=出库单号
- 补料出库：consume_type='2', ref_bill_type='OV', ref_bill_id=补料单号
- 报废出库：consume_type='3', ref_bill_type='OV', ref_bill_id=报废单号
- 返修出库：consume_type='4', ref_bill_type='OV', ref_bill_id=返修单号
- 退料入库：consume_type='5', ref_bill_type='IV', ref_bill_id=退料单号

**前端展示**：MaterialConsumeList.vue 分类型、分工单汇总显示

#### 3.3.4 过程记录表设计

```sql
CREATE TABLE tms05_replace_record (
    id SERIAL PRIMARY KEY,
    wo_id VARCHAR(20) NOT NULL COMMENT '工单号',
    old_eid VARCHAR(20) COMMENT '旧物料序列号（批次物料可为空）',
    new_eid VARCHAR(20) COMMENT '新物料序列号（批次物料可为空，FQC合格后生成）',
    itemcd VARCHAR(12) NOT NULL COMMENT '物料编码',
    old_batch_no VARCHAR(20) COMMENT '旧批次号（批次物料使用）',
    new_batch_no VARCHAR(20) COMMENT '新批次号（批次物料使用）',
    replace_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '更换时间',
    opercd VARCHAR(10) COMMENT '操作人',
    memo VARCHAR(200) COMMENT '备注'
);
CREATE INDEX idx_tms05_wo ON tms05_replace_record(wo_id);
```

**设计说明**：

- **EID 类型物料**：`old_eid`/`new_eid` 有值，`old_batch_no`/`new_batch_no` 为空。更换时同步更新 EID 状态表
- **批次物料（无 EID）**：`old_batch_no`/`new_batch_no` 有值，`old_eid`/`new_eid` 为空。批次号从补料单自动带出，FQC 合格后系统生成 EID 并回写到 `new_eid`
- 两种场景互斥：有 EID 则不需要批次号，有批次号则不需要 EID（当时尚未生成）

**前端展示位置**：工单列表抽屉（WorkOrderList.vue el-drawer）
- 更换按钮根据物料类型显示对应输入字段
- 批次物料：输入新旧批次号
- EID 物料：输入新旧 EID
- 更换历史按时间倒序显示

#### 3.3.5 未用料退料

工单审核（`COMPLETED`）时自动检查仓库中该工单 OV=8 的 **剩余库存**：

```sql
-- 查某工单补料出库中仍未使用的数量
SELECT ov.itemcd, ov.outqty - COALESCE(SUM(iv.inqty), 0) AS unused_qty
FROM twh15_out ov
LEFT JOIN twh13_in iv ON iv.refbillid = ov.outbillid
WHERE ov.refbillid = 'WO...' AND ov.invtyp = '8'
GROUP BY ov.itemcd, ov.outqty
HAVING ov.outqty - COALESCE(SUM(iv.inqty), 0) > 0;
```

生成退料单（IV=3 退货入库）：
- 自动创建 IV=3 入库单（auditflg='0'），物料退回原仓库
- TMS04 写入 consume_type='5'（退料）

**触发时机**：工单状态变为 COMPLETED 时（FQC 审核通过触发）。

## 5. 与行业方案对比

| 维度 | 本方案 | 行业常见做法 | 说明 |
|------|--------|-------------|------|
| 不良处理 | 行级判定 + 按行分流 | 整批判定 + 返修工单 | 行级更灵活，不需要返修工单管理成本 |
| 补料 | OV=8 草稿 + 独立审核 | 返修工单出库 / MRP 重排程 | 小批量场景 OV=8 更轻量 |
| 冗余量 | BOM 比率 | 固定数量 + 历史损耗率 | 比率更弹性，可衔接历史数据 |
| 退料 | 工单完成时自动检查 | 工单关闭时强制退料 | 时机一致，减少库存积压 |
| TMS04 | consume_type 区分来源 | 和工单 BOM 合并统计 | 区分后更容易核算废品成本 |

**选择本方案的原因**：
1. 不新增"返修工单"表，复杂度可控
2. OV=8 补料出库可复用现有仓库流程
3. 三个动作分离，各环节独立可操作
4. TMS04 扩展字段打通"QC → 仓库 → 成本"全链路

## 6. 物料分类说明

| 类型 | 表字段 | 判断逻辑 | 代码实际判断方式 | 补料行为 |
|------|--------|---------|----------------|---------|
| 成品 | `tmm12_items.typflg='1'` | BOM 存在 | BOM 表存在性判断 `is_bom` | 不补料（成品不合格整个工单不合格） |
| 配件 | `tmm12_items.typflg='0'` + `consume='0'` | 非成品非耗材 | `typflg='0'` + `consume='0'` | 需要补料 |
| 耗材 | `tmm12_items.consume='1'` | consume 字段 | `consume='1'` | 需要补料 |

**说明**：后端 `_enrich_item_names()` 使用 BOM 表存在性判断 `is_bom` 判断成品，前端 QC 结果页使用 `typflg` 和 `consume` 字段判断。两种方式在实际使用中行为一致，建议后续统一判断逻辑。

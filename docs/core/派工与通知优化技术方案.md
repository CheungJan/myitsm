# 派工与通知优化技术方案

## 1. 背景与目标

### 1.1 问题来源

在对齐 PB `w_r_itsm_dispatch.srw`（派工窗口）与 `of_newfetion`（飞信生成）数据流时，发现当前重构存在 6 个 UI/校验问题 + 通知流程缺失：

**6 个 UI/校验问题**：
1. 分派组下拉无数据源（`<el-input>` 未加载 `tmc12_groups`）
2. 新建派工分派组默认空且下拉无候选组
3. 新建派工操作员应为当前登录员工
4. 编辑功能操作员显示编码而非姓名
5. 已发送通知的派工记录仍可编辑
6. 已关闭状态单据仍可新增派工

**通知流程缺失**：
- `DispatchService.create` 只建派工记录，不建通知
- PB `of_newfetion` 自动生成 `TIT22_FETION_SEND`(sent_status='0') → 打开飞信编辑窗口 → 用户编辑发送 → sent_status='1' 的流程完全丢失
- 已有 `TNTF02_NOTIFICATION` 表 + `NotificationService` + `/api/v1/notification` API，但未与派工联动

### 1.2 目标

**第一阶段**：
- 修复 6 个 UI/校验问题
- 新增派单规则引擎 `tit30_dispatch_rule`（可配置故障类型→默认组/区域负责人映射）
- `tmc12_groups` 加 `leader_cd`（组长），与区域 `usercd` 对称
- 派工创建自动建 Notification（模板渲染，对齐 PB `of_newfetion`）
- 派工 Tab 通知状态列加"编辑通知"入口
- 维护单列表加"派给我"/"本区域"Tab 筛选

**第二阶段（后续）**：
- 真实短信/邮件网关对接
- 通知发送失败重试
- 通知模板可视化编辑器

## 3. 方案设计

### 3.1 派单规则引擎

#### 3.1.1 核心表 `tit30_dispatch_rule`（新增）

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| rule_id | serial PK | 规则ID | 1 |
| rule_name | varchar(50) | 规则名称 | POS故障→区域负责人 |
| priority | int | 优先级（小优先） | 10 |
| fault_type | varchar(2) | 故障类型（GZ字典，空=全匹配） | 1=POS |
| store_id | varchar(8) | 门店编码（可选，第一阶段留空，后续扩展VIP门店定向派单） | NULL |
| target_type | varchar(20) | 派单目标 | `area_manager` / `group_leader` / `manual` |
| target_value | varchar(20) | 目标值（area_manager/manual 时留空，group_leader 时=组编码） | A1 |
| fallback_type | varchar(20) | 一级兜底目标 | `group_leader` / `manual` |
| fallback_value | varchar(20) | 一级兜底值 | A1 |
| ultimate_fallback_type | varchar(20) | 最终兜底目标 | `group_leader` / `manual` |
| ultimate_fallback_value | varchar(20) | 最终兜底值 | A1 |
| useflg | varchar(1) | 有效标志 | 1 |
| auto_dispatch | varchar(1) | 自动派单开关: 1=启用/0=禁用 | 1 |
| creator | varchar(6) | 创建人 | admin |
| create_time | timestamp | 创建时间 | |
| updator | varchar(6) | 更新人 | |
| update_time | timestamp | 更新时间 | |

**target_type 枚举**：
- `area_manager`：派给区域负责人（`tmm46_area.usercd`）
- `group_leader`：派给组长（`tmc12_groups.leader_cd`）
- `manual`：不自动派，`accpectder` 留空，列表标"待人工分派"

**fallback 链式兜底**（最多两级）：
```
target → 无命中
  → fallback → 无命中
    → ultimate_fallback
  → ultimate_fallback（fallback 为 manual 时跳过）
```

#### 3.1.2 预置规则

| priority | fault_type | target_type | target_value | fallback_type | fallback_value | ultimate_fallback_type | ultimate_fallback_value | 含义 |
|----------|------------|-------------|--------------|---------------|----------------|------------------------|------------------------|------|
| 10 | 1=POS | area_manager | - | group_leader | A1 | manual | - | POS→区域负责人→A1组长→待人工 |
| 20 | 2=视频 | group_leader | A1 | group_leader | TT | manual | - | 视频→A1组长→TT组长→待人工 |
| 30 | 3=取机 | area_manager | - | group_leader | A1 | manual | - | 取机→区域负责人→A1组长→待人工 |
| 99 | 空 | group_leader | A1 | manual | - | - | - | 兜底→A1组长→待人工 |

#### 3.1.3 `tmc12_groups` 加 `leader_cd` 字段

```sql
ALTER TABLE tmc12_groups ADD COLUMN leader_cd varchar(6);
COMMENT ON COLUMN tmc12_groups.leader_cd IS '组长用户编码（tmc13_users.user_cd）';
```

与区域 `tmm46_area.usercd` 对称：

| 概念 | 区域 | 组 |
|------|------|-----|
| 负责人 | `tmm46_area.usercd` | `tmc12_groups.leader_cd`（新增）|
| 成员池 | `tit06_userarea` | `tmc21_usergroup` |
| 转派候选 | 区域成员 | 组成员 |

### 3.2 派单流程

```
维护单创建（fault_type + store_id）
  ↓
规则引擎匹配 tit30_dispatch_rule（按 priority 升序，fault_type 匹配）
  ↓
target_type=area_manager
  ├─ 查 tmm22_customers.area_cd → tmm46_area.usercd
  ├─ 有区域负责人 → accpectder=负责人，accpectd_group=默认组（A1）
  └─ 无区域负责人 → 用 fallback
     └─ fallback_type=group_leader → accpectder=A1.leader_cd，accpectd_group=A1
  ↓
target_type=group_leader
  ├─ 查 tmc12_groups.leader_cd
  ├─ 有组长 → accpectder=组长，accpectd_group=组编码
  └─ 无组长 → 用 fallback（递归，最多两层）
  ↓
无规则命中 → 兜底规则（priority=99）→ A1组长
  ↓
插入 tit21_maintenance_dispatch
  ↓
自动建 Notification（ref_type='dispatch', ref_id=maintenance_id, recipient=accpectder）
```

#### 分派人候选筛选逻辑

分派人下拉候选按**组切换行为**区别处理：

| 场景 | 候选范围 |
|------|---------|
| **初始打开表单**（默认组 A1） | 全部区域人员（`tit06_userarea` choose=1），不筛选 |
| **手动切换组**（如 A1→TT） | 所选组成员 **∩** 区域人员（交集） |
| 区域负责人 | 始终在候选列表**顶部**，无论是否在筛选结果中 |

**交集示例**：JS 区域有 3 人（周佳 576、朱利刚 1870、张剑 1612），切换组为 TT 后仅显示 1 人（张剑 1612 ∈ TT ∩ JS）。

> `accpectd_group` 的双重角色：① 规则引擎兜底（`fallback_type=group_leader`）② 手动派工时按组筛选分派人候选。

### 3.3 通知联动

#### 3.3.1 通知模板（预置 `tntf01_template`）

| template_id | template_name | channel | subject | body |
|-------------|---------------|---------|---------|------|
| DISPATCH | 派工通知 | internal | 【派工通知】{maintenance_id} | 客户卡号:{cust_card}\n维护单号:{maintenance_id}\n请求时间:{request_time}\n客户名:{cust_nm}\n地址:{address}\n电话:{phone_no}\n故障描述:{short_description}\n分派人:{accpectder_nm} |

body 使用 Jinja2 占位符，渲染时从维护单 + 客户 + 派工记录取值。

#### 3.3.2 派工创建自动建通知

`DispatchService.create` 成功后：
1. 用 `DISPATCH` 模板渲染 body（从 maintenance_id 关联查询字段）
2. **创建时一次性渲染（快照语义）**：派工创建后客户信息可能变更（改地址/电话），但通知应反映派工当时的快照，因此渲染结果固化到 `tntf02_notification.body`，后续展示/发送均用此快照
3. 插入 `tntf02_notification`：
   - `template_id='DISPATCH'`
   - `channel='internal'`
   - `recipient=accpectder`
   - `subject`=渲染后标题
   - `body`=渲染后正文
   - `ref_type='dispatch'`
   - `ref_id=maintenance_id`
   - `send_status='pending'`
3. `_enrich_notify_status` 已实现回填 `notify_status`/`notify_data` 到派工列表

#### 3.3.3 通知编辑入口（对齐 PB `w_r_itsm_fetion`）

派工 Tab 通知状态列：
- `notify_status='pending'` → 显示"编辑通知"按钮 → 跳转通知管理页面，预填模板内容，可编辑后点"发送"
- `notify_status='sent'` → 显示"已发送"标签，无编辑按钮（问题5修复）
- `notify_status='N'`（无通知记录）→ 显示"生成通知"按钮

发送 → `NotificationService.send` → `send_status='sent'` + `send_time`（第一阶段仅落库）

### 3.4 维护单列表 Tab 筛选

维护单列表顶部加 Tab：

```
[全部] [派给我] [本区域]
```

- **全部**：现有列表，无过滤
- **派给我**：`accpectder = 当前用户`（所有登录用户可见）
- **本区域**：`area_cd = 当前用户负责的区域`（仅当 `tmm46_area.usercd = 当前用户` 时显示此 Tab）

## 5. 数据流图

### 5.1 派单+通知完整流程

```
一线客服创建维护单（磁卡号 + 故障类型 + 简述）
  ↓
MaintenanceDailyService.create
  ↓
DispatchService.auto_create
  ├─ 规则引擎匹配 tit30_dispatch_rule（按 fault_type）
  ├─ target_type=area_manager → 查区域负责人
  ├─ target_type=group_leader → 查组长
  └─ 兜底 → A1组长
  ↓
插入 tit21_maintenance_dispatch（accpectder=负责人/组长）
  ↓
NotificationService.create（用 DISPATCH 模板渲染）
  ↓
插入 tntf02_notification（send_status='pending', recipient=accpectder）
  ↓
区域负责人/组长登录
  → 维护单列表"派给我"Tab → 看到 accpectder=自己 的单
  → 打开单据 → 派工 Tab
     ├─ 看到自动派工记录 + 通知状态(pending)
     ├─ 点"编辑通知" → 通知管理页面 → 编辑内容 → 发送 → send_status='sent'
     └─ 点"新增派工" → 转派给区域成员/组成员
        ↓
        新派工记录 + 新 Notification(pending)
        ↓
        被转派人在"派给我"Tab 看到新单
```

#### 10.4.4 Gateway 基类

# app/services/gateways/base.py
from abc import ABC, abstractmethod

class BaseGateway(ABC):
    """通知网关抽象基类。"""

    @abstractmethod
    def send(self, recipient: str, subject: str, body: str) -> tuple[bool, str]:
        """发送通知，返回 (是否成功, 错误信息)。"""
        raise NotImplementedError

#### 10.4.5 NotificationService.send 改造

```python
# app/services/notification_service.py
@staticmethod
def send(notification_id: int) -> dict[str, Any] | None:
    record = NotificationRepository.get_by_id(notification_id)
    if record is None:
        return None
    if record.send_status == "sent":
        return record.to_dict()

    gateway = GatewayFactory.get(record.channel)
    if gateway is None:
        NotificationRepository.mark_failed(record, f"不支持渠道: {record.channel}")
        db.session.commit()
        return record.to_dict()

    try:
        success, error = gateway.send(record.recipient, record.subject or "", record.body or "")
        if success:
            NotificationRepository.mark_sent(record)
            record.error_msg = None
        else:
            NotificationRepository.mark_failed(record, error or "未知错误")
    except Exception as e:
        NotificationRepository.mark_failed(record, str(e))
    db.session.commit()
    return record.to_dict()
```

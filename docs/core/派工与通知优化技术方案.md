# 派工与通知优化技术方案

## 1. 背景与目标

### 1.1 问题来源

在对齐 PB `w_r_itsm_dispatch.srw`（派工窗口）与 `of_newfetion`（飞信生成）数据流时，发现当前重构存在 6 个 UI/校验问题 + 通知流程缺失：

**6 个 UI/校验问题**：
1. 分派组下拉无数据源（`<el-input>` 未加载 `tmc12_groups`）
2. 新建派工分派组默认空且下拉无候选组
3. 新建派工操作员应为当前登录员工
4. 编辑功能操作员显示编码而非姓名
5. 已发送通知的派工记录仍可编辑
6. 已关闭状态单据仍可新增派工

**通知流程缺失**：
- `DispatchService.create` 只建派工记录，不建通知
- PB `of_newfetion` 自动生成 `TIT22_FETION_SEND`(sent_status='0') → 打开飞信编辑窗口 → 用户编辑发送 → sent_status='1' 的流程完全丢失
- 已有 `TNTF02_NOTIFICATION` 表 + `NotificationService` + `/api/v1/notification` API，但未与派工联动

### 1.2 目标

**第一阶段**：
- 修复 6 个 UI/校验问题
- 新增派单规则引擎 `tit30_dispatch_rule`（可配置故障类型→默认组/区域负责人映射）
- `tmc12_groups` 加 `leader_cd`（组长），与区域 `usercd` 对称
- 派工创建自动建 Notification（模板渲染，对齐 PB `of_newfetion`）
- 派工 Tab 通知状态列加"编辑通知"入口
- 维护单列表加"派给我"/"本区域"Tab 筛选

**第二阶段（后续）**：
- 真实短信/邮件网关对接
- 通知发送失败重试
- 通知模板可视化编辑器

## 3. 方案设计

### 3.1 派单规则引擎

#### 3.1.1 核心表 `tit30_dispatch_rule`（新增）

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| rule_id | serial PK | 规则ID | 1 |
| rule_name | varchar(50) | 规则名称 | POS故障→区域负责人 |
| priority | int | 优先级（小优先） | 10 |
| fault_type | varchar(2) | 故障类型（GZ字典，空=全匹配） | 1=POS |
| store_id | varchar(8) | 门店编码（可选，第一阶段留空，后续扩展VIP门店定向派单） | NULL |
| target_type | varchar(20) | 派单目标 | `area_manager` / `group_leader` / `manual` |
| target_value | varchar(20) | 目标值（area_manager/manual 时留空，group_leader 时=组编码） | A1 |
| fallback_type | varchar(20) | 一级兜底目标 | `group_leader` / `manual` |
| fallback_value | varchar(20) | 一级兜底值 | A1 |
| ultimate_fallback_type | varchar(20) | 最终兜底目标 | `group_leader` / `manual` |
| ultimate_fallback_value | varchar(20) | 最终兜底值 | A1 |
| useflg | varchar(1) | 有效标志 | 1 |
| auto_dispatch | varchar(1) | 自动派单开关: 1=启用/0=禁用 | 1 |
| creator | varchar(6) | 创建人 | admin |
| create_time | timestamp | 创建时间 | |
| updator | varchar(6) | 更新人 | |
| update_time | timestamp | 更新时间 | |

**target_type 枚举**：
- `area_manager`：派给区域负责人（`tmm46_area.usercd`）
- `group_leader`：派给组长（`tmc12_groups.leader_cd`）
- `manual`：不自动派，`accpectder` 留空，列表标"待人工分派"

**fallback 链式兜底**（最多两级）：
```
target → 无命中
  → fallback → 无命中
    → ultimate_fallback
  → ultimate_fallback（fallback 为 manual 时跳过）
```

#### 3.1.2 预置规则

| priority | fault_type | target_type | target_value | fallback_type | fallback_value | ultimate_fallback_type | ultimate_fallback_value | 含义 |
|----------|------------|-------------|--------------|---------------|----------------|------------------------|------------------------|------|
| 10 | 1=POS | area_manager | - | group_leader | A1 | manual | - | POS→区域负责人→A1组长→待人工 |
| 20 | 2=视频 | group_leader | A1 | group_leader | TT | manual | - | 视频→A1组长→TT组长→待人工 |
| 30 | 3=取机 | area_manager | - | group_leader | A1 | manual | - | 取机→区域负责人→A1组长→待人工 |
| 99 | 空 | group_leader | A1 | manual | - | - | - | 兜底→A1组长→待人工 |

#### 3.1.3 `tmc12_groups` 加 `leader_cd` 字段

```sql
ALTER TABLE tmc12_groups ADD COLUMN leader_cd varchar(6);
COMMENT ON COLUMN tmc12_groups.leader_cd IS '组长用户编码（tmc13_users.user_cd）';
```

与区域 `tmm46_area.usercd` 对称：

| 概念 | 区域 | 组 |
|------|------|-----|
| 负责人 | `tmm46_area.usercd` | `tmc12_groups.leader_cd`（新增）|
| 成员池 | `tit06_userarea` | `tmc21_usergroup` |
| 转派候选 | 区域成员 | 组成员 |

### 3.2 派单流程

```
维护单创建（fault_type + store_id）
  ↓
规则引擎匹配 tit30_dispatch_rule（按 priority 升序，fault_type 匹配）
  ↓
target_type=area_manager
  ├─ 查 tmm22_customers.area_cd → tmm46_area.usercd
  ├─ 有区域负责人 → accpectder=负责人，accpectd_group=默认组（A1）
  └─ 无区域负责人 → 用 fallback
     └─ fallback_type=group_leader → accpectder=A1.leader_cd，accpectd_group=A1
  ↓
target_type=group_leader
  ├─ 查 tmc12_groups.leader_cd
  ├─ 有组长 → accpectder=组长，accpectd_group=组编码
  └─ 无组长 → 用 fallback（递归，最多两层）
  ↓
无规则命中 → 兜底规则（priority=99）→ A1组长
  ↓
插入 tit21_maintenance_dispatch
  ↓
自动建 Notification（ref_type='dispatch', ref_id=maintenance_id, recipient=accpectder）
```

### 3.3 通知联动

#### 3.3.1 通知模板（预置 `tntf01_template`，2026-07-17 扩展）

**模型扩展**：`ref_type`（业务类型）+ `is_default`（默认模板）+ `sort_no`（排序号）。

| template_id | ref_type | is_default | 说明 |
|-------------|----------|:---:|------|
| DISPATCH | dispatch | 1 | 派工通知默认模板 |
| *（自定义）* | dispatch/maintenance/... | 0/1 | 用户自定义，sort_no 排序 |

**可用变量（24 个）**：`_build_notify_context` 从维护单+客户+派工记录提取：

```
maintenance_id, store_id, cust_card, cust_nm, address, phone_no, contactor,
accpectder, accpectder_nm, accpectd_group, fault_type, fault_type_nm,
short_description, request_time, current_status, current_status_nm,
urgency, operator, dispatch_time, area_cd, area_nm, company_id, ...
```

**模板选择优先级**（`_create_notification`）：
1. 调用方指定的 `template_id`
2. `ref_type='dispatch'` 下 `is_default='1'` 的模板
3. `template_id='DISPATCH'`（兼容旧数据）

**前端功能**：
- 模板列表：业务类型筛选 + 默认标记列 + 排序号 + 设为默认按钮
- 编辑器：变量按钮（24个） + Jinja2 实时预览（400ms 防抖）
- `DispatchNotifyEditor`：按 `ref_type=dispatch` 加载模板下拉，默认选 `is_default='1'`

#### 3.3.2 派工创建自动建通知（自动派工）

`DispatchService.auto_create` 按 `tit30_dispatch_rule.notify_channel` 配置自动发送：

```
auto_create → DispatchRuleService.resolve
  → notify_channel 取规则配置（默认 internal）
  → _create_notification(record, ..., channel=notify_channel)
    → 渲染 DISPATCH 模板快照 → 插入 tntf02_notification
    → 自动调 NotificationService.send → send_status='sent'
```

**自动派工 = 派工记录 + 通知记录 + 自动发送，一步完成。**

#### 3.3.3 手动派工 → 消息编辑器集成（方案 A，已落地）

手动派工表单（`ItsmSubTablePane`）底部集成 `DispatchNotifyEditor` 组件：

```
┌─ 新增派工 ────────────────────────┐
│ 操作员 / 分派组 / 分派人 / 派工时间  │
├─ 消息编辑（DispatchNotifyEditor）──┤
│ 模板: [DISPATCH] ← 自动渲染        │
│ 标题: 【派工通知】MD065397         │
│ 正文: 客户卡号:xxx ...（可编辑）    │
│ 渠道: [internal] [dingtalk] [email]│
├────────────────────────────────────┤
│  [取消]  [仅保存]  [保存并发送]      │
└────────────────────────────────────┘
```

两个按钮：
- **仅保存**：`submitForm()` → 只建派工记录，不发送通知（通知记录仍创建，`send_status='pending'`，后续可在派工列表中点"发送"）
- **保存并发送**：`submitAndSend()` → `submitForm()` + 读取编辑器内容 → `sendDispatchNotification(record_id, {channel, subject, body})` → 后端调 Gateway 真实发送

**与 PB 对比**：PB 点"派工"→ 弹窗选分派人+消息→ 点"发送"完成。重构版本在此基础上增加模板渲染预览、多渠道选择、仅保存灵活性，比 PB 更好。

#### 3.3.4 派工列表通知状态列

| 状态 | 显示 | 操作 |
|------|------|------|
| `sent` | 已发送 | ✅ 已读/未读标签 |
| `pending` | 未发 | [发送] 按钮 → 弹出 `DispatchNotifyEditor` → 编辑 → 发送 |
| `N` | 无记录 | — |

## 5. 数据流图

### 5.1 派单+通知完整流程

```
一线客服创建维护单（磁卡号 + 故障类型 + 简述）
  ↓
MaintenanceDailyService.create
  ↓
DispatchService.auto_create
  ├─ 规则引擎匹配 tit30_dispatch_rule（按 fault_type）
  ├─ target_type=area_manager → 查区域负责人
  ├─ target_type=group_leader → 查组长
  └─ 兜底 → A1组长
  ↓
插入 tit21_maintenance_dispatch（accpectder=负责人/组长）
  ↓
NotificationService.create（用 DISPATCH 模板渲染）
  ↓
插入 tntf02_notification（send_status='pending', recipient=accpectder）
  ↓
区域负责人/组长登录
  → 维护单列表"派给我"Tab → 看到 accpectder=自己 的单
  → 打开单据 → 派工 Tab
     ├─ 看到自动派工记录 + 通知状态(pending)
     ├─ 点"编辑通知" → 通知管理页面 → 编辑内容 → 发送 → send_status='sent'
     └─ 点"新增派工" → 转派给区域成员/组成员
        ↓
        新派工记录 + 新 Notification(pending)
        ↓
        被转派人在"派给我"Tab 看到新单
```

from abc import ABC, abstractmethod

class BaseGateway(ABC):
    """通知网关抽象基类。"""

    @abstractmethod
    def send(self, recipient: str, subject: str, body: str) -> tuple[bool, str]:
        """发送通知，返回 (是否成功, 错误信息)。"""
        raise NotImplementedError

#### 10.4.5 NotificationService.send 改造

```python
# app/services/notification_service.py
@staticmethod
def send(notification_id: int) -> dict[str, Any] | None:
    record = NotificationRepository.get_by_id(notification_id)
    if record is None:
        return None
    if record.send_status == "sent":
        return record.to_dict()

    gateway = GatewayFactory.get(record.channel)
    if gateway is None:
        NotificationRepository.mark_failed(record, f"不支持渠道: {record.channel}")
        db.session.commit()
        return record.to_dict()

    try:
        success, error = gateway.send(record.recipient, record.subject or "", record.body or "")
        if success:
            NotificationRepository.mark_sent(record)
            record.error_msg = None
        else:
            NotificationRepository.mark_failed(record, error or "未知错误")
    except Exception as e:
        NotificationRepository.mark_failed(record, str(e))
    db.session.commit()
    return record.to_dict()
```

## 11. 问题与解决（2026-07-17 第四阶段打磨）

本轮聚焦三大问题域：通知列表标记已读失效、铃铛通知点击交互、派工-通知流水号对齐。

### 11.1 通知列表标记已读全部失效

**现象**：
- "标为已读"按钮点击无效，手动刷新也不变
- 打开通知详情弹窗关闭后未自动标记已读
- 勾选多条后"已读选中"无效果
- 但右上角铃铛点击通知后未读数字会减少

**根因**：`NotificationList.vue` 中所有操作使用了 `row.notification_id`，但 Notification 模型的 PK 列名是 `id`，`to_dict()` 返回的 JSON 中字段名为 `id`。`row.notification_id` 始终为 `undefined`，所有 API 请求发往 `/notifications/undefined/read`，Flask 路由匹配失败，请求静默失败。

**解决**：全局替换 `notification_id` → `id`（共 4 处：`onSelectionChange`、`markAllRead`、`handleRead`、`handleSend`、watch drawer 比较）。

**涉及文件**：`frontend/src/views/notification/NotificationList.vue`

### 11.2 新增派工后通知 tab 不显示新记录

**现象**：在派工 tab 新增派工并发送通知后，切换到"通知记录"tab，新通知不出现。手动刷新浏览器才看到。

**根因**：
1. `ItsmSubTablePane` 派工保存后 emit `sent` 事件，但 `MaintenanceList.vue` 未监听 `@sent`
2. 切换到"通知记录"tab 时未触发重新加载（`notifyList` 仅在 `detail` 变化时加载一次）

**解决**：
1. 派工组件加 `@sent="onDispatchSent"` `@saved="onDispatchSaved"`
2. 添加 `watch(activeTab)` → 切换到 `'notify'` 时自动 `loadNotifyList()`
3. 提取 `loadNotifyList()` 函数消除 3 处重复的通知加载代码

**涉及文件**：`frontend/src/views/itsm/MaintenanceList.vue`

### 11.3 通知列表缺少可见序号

**现象**：通知 tab 列表中无序号列，用户无法直观看到当前有几条记录、最新记录位置。

**解决**：添加流水号列 `<el-table-column prop="dispatch_id" label="流水号" />`。`dispatch_id` 与派工的 `business_operation_id` 对齐——同维护单内按时间从 1 递增。

**涉及文件**：`frontend/src/views/itsm/MaintenanceList.vue`、`frontend/src/views/notification/NotificationList.vue`

### 11.4 dispatch_id 值错误（派工 PK 混入）

**现象**：`tntf02_notification.dispatch_id` 存储的是 `tit21_maintenance_dispatch.id`（派工表自增 PK，如 150078），而非同单内的流水序号。

**根因**：`DispatchService.send_notification` 中 `"dispatch_id": record.id` 错误地将派工记录 PK 赋值给了通知流水号。

**解决**：
- `dispatch_id` 改为 `record.business_operation_id`（派工的同单流水号），与派工表共享同一序号体系
- 历史数据通过时间最近匹配修复 38,021 条

**涉及文件**：`app/services/itsm_service.py`（`send_notification` 方法）

### 11.5 `_enrich_notify_status` 匹配断裂

**现象**：修复 `dispatch_id` 后，派工列表通知状态列全部显示"未发"/"未产生"。

**根因**：`_enrich_notify_status` 原逻辑用 `Notification.dispatch_id` 匹配派工 PK（`r.get("id")`）。改 `dispatch_id` 为序号后匹配断裂。

**解决**：改为双键匹配 `(ref_id, dispatch_id)` ↔ `(maintenance_id, business_operation_id)`。两个序号一一对应，无需新增字段。

**涉及文件**：`app/services/itsm_service.py`（`_enrich_notify_status` 函数）

### 11.6 通知列表排序方向

**现象**：通知默认 `order_by(gendate DESC)`（最新在前），`type="index"` 序号 1 = 最新记录 = 最大 ID，视觉上序号和 ID 增长方向相反。

**解决**：保持 `DESC` 默认（最新在前），添加 `order` API 参数支持双向排序。铃铛传 `order=desc` 获取最新通知，列表页默认 `desc`。

**涉及文件**：`app/repositories/notification_repository.py`、`app/services/notification_service.py`、`app/api/notification.py`、`NotificationBell.vue`

### 11.7 铃铛通知点击无响应（关键）

**现象**：点击铃铛弹出通知列表后，点击通知条目无任何反应——不标记已读、不跳转、Console 无输出。

**排查过程**：
1. 最初怀疑 `notification_id` vs `id` 字段名问题 → 铃铛用 `n.id`（正确），排除
2. 怀疑 API 调用失败被 `catch{}` 静默吞错 → 加 `console.log` 仍无输出，排除
3. 怀疑 `router.push` 参数问题 → 改 `name` 为 `path` 仍无效，排除
4. **最终发现**：`el-popover` 的 `trigger="click"` 拦截了内部元素的所有点击事件，`@click="handleClick(n)"` 从未执行

**根因**：Element Plus `el-popover` 组件内部事件机制拦截了 popover 内容区域的点击事件，导致 Vue 的 `@click` 绑定完全失效。

**解决**：完全移除 `el-popover`，改为纯手工实现：
- `v-if="popVisible"` 控制显隐
- `position: absolute` 定位下拉面板
- `document.addEventListener('click')` 监听外部点击自动关闭
- 原生 `@click` 绑定，无中间层拦截

**涉及文件**：`frontend/src/components/common/NotificationBell.vue`（重写）

### 11.8 铃铛通知点击后的交互模式

**现象**：即使点击事件生效，在铃铛弹窗内原地标记已读的交互模式也不符合行业惯例。

**行业标准**：点击通知 → 跳转到关联业务页面查看上下文 → 查看动作自然标记已读（GitHub→PR、Jira→工单、飞书→消息）。

**解决**：铃铛点击通知后：
1. 调用 API 标记已读
2. 关闭铃铛面板
3. `router.push` 跳转到 `/itsm/maintenance?maintenance_id={ref_id}&tab=notify`
4. `MaintenanceList.vue` 的 `onMounted` 读取 query 参数，自动筛选工单、打开详情、切换到通知记录 tab

**涉及文件**：`NotificationBell.vue`（handleClick）、`MaintenanceList.vue`（onMounted + useRoute）

### 11.9 MaintenanceList.vue 缺少 `useRoute`

**现象**：铃铛跳转后报 `ReferenceError: route is not defined`。

**解决**：添加 `import { useRoute } from 'vue-router'` 和 `const route = useRoute()`。

**涉及文件**：`frontend/src/views/itsm/MaintenanceList.vue`

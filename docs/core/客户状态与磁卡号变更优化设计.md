# 客户状态与磁卡号变更优化设计

> 本文档总结 myitsm 项目（PB→Python 重构）中针对**客户生命周期状态管理**与**磁卡号变更业务（CK/BQ/BG）**的优化设计，覆盖业务语义、数据模型、服务层实现、历史追溯与迁移验证。

> ⚠️ **阅读提示**：第 1-10 章为早期基于 PB 界面层推断的设计；**第 11 章基于 Oracle 存储过程真实源码逐行还原，为最高权威依据**，已修正前文若干错误结论（客户失效三维度、两阶段接口、cust_useflg 真实语义）。结论冲突时以第 11 章为准。

## 1. 背景与问题

### 1.1 PB 原系统缺陷

| 问题 | PB 原系统行为 | 影响 |
|---|---|---|
| 客户状态缺失 | `tmm22_customers` 无生命周期字段，客户"永久有效" | 预计划取消后客户仍可见，产生"幽灵客户" |
| 磁卡号变更无历史 | CK 类型直接覆盖 `custcard`，旧卡号丢失 | 无法追溯换卡历史，审计断链 |
| BQ 信息变更无留痕 | 直接 UPDATE 客户表，无变更快照 | 无法对比联系人/电话/地址的历史变更 |
| 变更类型语义模糊 | `change_type` 字段含义不清晰 | 迁移后出现数字码 `10/30` 与字母码 `CK/BQ/BG` 混用 |

### 1.2 优化目标

1. **客户生命周期可管理**：TEMP → PENDING → ACTIVE → INVALID 四态机
2. **磁卡号变更可追溯**：CK/BG 变更时保存旧/新磁卡号到历史表
3. **信息变更可审计**：BQ 变更时保存旧/新信息快照
4. **变更类型语义清晰**：统一使用字母码 CK/BQ/BG

## 2. 客户生命周期状态机

### 2.1 状态定义

| 状态        | 含义   | 触发场景          |
| --------- | ---- | ------------- |
| `TEMP`    | 临时客户 | 预计划新建（客户表无记录） |
| `PENDING` | 待确认  | 预计划提交/实施确认    |
| `ACTIVE`  | 正式客户 | 预计划完成（下游单据审核） |
| `INVALID` | 已作废  | 预计划作废（临时客户降级） |

### 2.2 状态流转图

```
  ┌─────────┐  创建   ┌─────────┐  提交   ┌─────────┐
  │  (无)   │────────▶│  TEMP   │────────▶│ PENDING │
  └─────────┘         └─────────┘         └─────────┘
                           │                    │
                           │ 作废               │ 作废
                           ▼                    ▼
                      ┌─────────┐         ┌─────────┐
                      │ INVALID │         │ INVALID │
                      └─────────┘         └─────────┘
                                              │
                                              │ 完成
                                              ▼
                                         ┌─────────┐
                                         │ ACTIVE  │
                                         └─────────┘
```

### 2.3 关键规则

- **老客户保护**：已有 `ACTIVE` 客户不会被降级为 `TEMP`（`CustomerService.create_temp_customer` 逻辑）
- **老客户不降级**：取机回收（plantyp=30）、关门（plantyp=40）、翻新（plantyp=20）必然是老客户，保持 `ACTIVE`
- **迁移默认值**：历史数据迁移时 `customer_status` 跳过写入，使用模型默认 `ACTIVE`（`app/migration/field_mapper.py:10-16`）

### 2.4 新客户判定

| plantyp | 客户表情况 | 是否新客户 | 处理 |
|---|---|---|---|
| `00` 全新开通 | `cust_cd` 不存在 | ✓ 新客户 | 创建 TEMP |
| `10` 磁卡号变更 | `cust_cd`（当前门店）已存在 | ✗ 老客户 | 更新 `cust_card`，保持 ACTIVE |
| `10` 磁卡号变更 | `new_cust_cd`（源门店）已存在 | ✗ 老客户 | 关单时 `useflg='0'`（无条件失效） |
| `20` 翻新 | `cust_cd` 已存在 | ✗ 老客户 | 保持 ACTIVE |
| `30` 取回 | `cust_cd` 已存在 | ✗ 老客户 | 保持 ACTIVE |
| `40` 关门 | `cust_cd` 已存在 | ✗ 老客户 | 保持 ACTIVE |

**关键概念**：
- `cust_cd` = 客户业务主键（法人/门店主体），终身不变
- `cust_card` = 磁卡号（物理介质标识），可更换
- **新客户 = `cust_cd` 在客户表不存在**（只有全新开通 plantyp=00 才可能新建）
- **磁卡号变更 ≠ 新客户**（老客户换卡，只更新 `cust_card` 字段）
- **plantyp=10 两端都是老客户**：`cust_cd`（当前门店）+ `new_cust_cd`（源门店）都必须已存在于客户表，不涉及新客户创建

> **⚠️ 前端磁卡号输入**（2026-07-02）：plantyp=00（全新开通）和 plantyp=10（磁卡号变更）的磁卡号字段支持手动输入，因为全新开通针对新用户、磁卡号变更是老用户新磁卡号，这些记录在系统客户表中不存在。但 `cust_cd`（客户编码）仍需用户填写，后端 `create_temp_customer` 据此判断是否新客户。

> **⚠️ custcd 自动生成**（2026-07-02）：plantyp=00 全新开通时若用户未填 `cust_cd`，后端 `CustomerService.generate_custcd` 按 PB 规则自动生成：`MAX(cust_cd)+1`，左侧补零到 8 位（对齐 PB `w_plan_cust_befor_new.srw`）。生成后回写到预计划记录，保证客户主数据唯一性。plantyp=10 磁卡号变更两端都是老客户，`cust_cd` 必须已存在，不自动生成。

> **⚠️ 前端客户编码字段交互规则**（2026-07-03，对齐 PB `w_plan_cust_befor_new.srw`）：
> - **plantyp=00 全新开通**：客户编码字段**只读**，placeholder 提示"保存后自动生成"；用户输入磁卡号后保存，后端按 `MAX(cust_cd)+1` 左补零 8 位自动生成，前端从创建响应回填 `form.custcd`（对齐 PB `of_insert_cust: SetItem(ll_row, 'CustCd', ls_Custcd)`）
> - **其他 plantyp（10/20/30/40）**：客户编码字段**默认禁用空白**不允许填写，placeholder 提示"选择磁卡号后自动带出"；用户选择磁卡号后从已有客户记录联动带出 `custcd`，字段改为只读显示
> - **切换计划类型**：清空 `form.custcd`（切换到 00 待自动生成 / 切换到其他需重新选择磁卡号联动）
> - **实现位置**：`frontend/src/views/sales/PlanList.vue` `custcdReadonly`/`custcdDisabled`/`custcdPlaceholder` 计算属性 + `handleSave` 响应回填

> **⚠️ plantyp=00 复制新建模式**（2026-07-03，对齐 SAP XD01 "Refer to" / 用友客户档案复制 / Salesforce Clone）：
> - **业务场景**：连锁客户共用基础信息，如"一店"改"二店"或同街道新开门店，需基于已有 A 门店信息新建 B 门店
> - **交互规则**：plantyp=00 保留"选择"按钮，但语义从"选择已有客户"改为"**复制已有客户信息**"
>   - 选择后**复制**基础信息：`custnm`/`address`/`contactor`/`phoneno`/`classcd`/`busityp`/`pptcode`/`yun_type`/`commmode`/`is_contract`/`jl_contactor`/`jl_phoneno`/`custrnm`
>   - **强制清空**主键和唯一标识：`custcard`（要求输入新磁卡号）、`custcd`（保存后自动生成）
>   - **不加载**已有资产（新客户无历史设备）
>   - **提示**：`ElMessage.info('已基于客户 [XXX] 复制信息，请修改店名/地址并输入新磁卡号')`
> - **对话框标题**：plantyp=00 时显示"复制已有客户信息（新建）"，其他 plantyp 显示"选择目标客户"
> - **行业依据**：SAP XD01 "Refer to" 字段、Salesforce Clone、用友 U8 客户档案复制、Oracle EBS Party Copy 均采用此模式——**可复制业务信息，主键和唯一标识必须重新生成**
> - **实现位置**：`frontend/src/views/sales/PlanList.vue` `onCustSelect` target 分支按 `form.plantyp` 分流 + `custPickerTitle` 计算属性

> **⚠️ plantyp=10 磁卡号变更换卡业务模式**（2026-07-03，对齐银行换卡/会员换卡/门禁换卡行业标准）：
> - **业务本质**：老客户换新磁卡号，客户编码（主键）不变，磁卡号（唯一标识）变，基础信息从源门店（老客户）复制
> - **交互流程**（必须先选源门店）：
>   1. 用户先在"源设备块"点"选择" → 选源门店（老客户）→ `onCustSelect` source 分支处理
>   2. 选源门店后**同步基础信息**到当前客户字段：`custcd`（不变）+ `custrnm`/`contactor`/`phoneno`/`classcd`/`busityp`/`pptcode`/`yun_type`/`commmode`/`is_contract`/`jl_contactor`/`jl_phoneno`
>   3. **不同步**：`custnm`（店名可改）/`address`（地址可改）/`custcard`（新磁卡号用户输入）
>   4. `custcd` = 源门店 `cust_cd`（不变，对齐行业换卡业务"主键不变"原则）
>   5. 用户在磁卡号字段输入新磁卡号（`custcard`）
> - **磁卡号字段**（plantyp=10）：
>   - **隐藏"选择"按钮**（`showCustcardPickerBtn = form.plantyp !== '10'`），新磁卡号手动输入
>   - 未选源门店时 `disabled` 完全禁用交互（不可点击/不可选中/不可触发事件，对齐 `custcd` 模式）+ placeholder "请先选择源门店"，强制先选源
>   - 选源门店后可输入新磁卡号
> - **客户编码字段**（plantyp=10）：
>   - 未选源门店时 `disabled` + placeholder "选择源门店后自动带出"
>   - 选源门店后自动带入源门店 `cust_cd`，只读显示
> - **行业依据**：银行换卡（客户ID不变/卡号变）、会员系统换卡（会员ID不变/卡号变）、门禁换卡——通用原则"**主键不变 + 唯一标识变 + 业务信息从源复制**"
> - **实现位置**：`frontend/src/views/sales/PlanList.vue` `onCustSelect` source 分支 plantyp=10 同步逻辑 + `custcardReadonly`/`custcardPlaceholder`/`showCustcardPickerBtn`/`custcdDisabled`/`custcdPlaceholder` 计算属性 + `clearCustPicker` source 分支 plantyp=10 清理

> **⚠️ 字段命名约定**（2026-07-02）：`new_` 前缀在 PB 中表示"源"（source），不是"新"（new）：
> - `custcard` = 当前门店磁卡号（plantyp=00 新客户的新磁卡号 / plantyp=10 变更后的新磁卡号）
> - `new_custcard` = 源门店磁卡号（源磁卡号/老卡号，plantyp=10 移机时源门店的磁卡号）
> - `custcd` = 当前门店编码
> - `new_custcd` = 源门店编码（plantyp=10 移机时的源门店）

> **⚠️ 磁卡号录入规则**（2026-07-02，对齐 PB `d_plan_cust_edit.srd` + `w_plan_cust_befor.srw:of_insert_cust`）：
> - **长度限制**：`custcard` ≤ 20 字符（PB DataWindow `char(20)` + Oracle `VARCHAR2(20)`），API schema `max_length=20` + service 层双重校验
> - **磁卡号重复检查**（`custcard` = 当前门店磁卡号，需唯一）：
>   - plantyp=00 新客户创建时：在 `create_temp_customer` 中校验 `custcard`（`SELECT count(1) WHERE CUSTCARD=:ls AND USEFLG='1'`），重复则拒绝
>   - plantyp=10 磁卡号变更时：在 `sales_service.create` 中校验 `custcard`（变更后的新磁卡号），重复则拒绝
>   - plantyp=20/30/40：`custcard` 是老客户已有磁卡号，仍校验避免冲突
> - **源磁卡号 `new_custcard` 不校验**：`new_custcard` 是源门店老磁卡号，本来就在客户表中，不校验唯一性
> - **客户名称重复检查**：仅 plantyp=00 新客户创建时校验（`SELECT count(*), max(custcd) WHERE custnm=:ls`），同名则拒绝并提示已有 custcd
> - **大小写不限**：PB `edit.case=any`，重构不限制大小写
> - **实现位置**：`CustomerService.validate_custcard` / `validate_custnm_unique` / `create_temp_customer(plantyp=...)` / `sales_service.create`（`check_card_exists` + `find_by_custcard`）

## 3. 磁卡号变更业务（CK/BQ/BG）

> **⚠️ 2026-07-02 重大修正**：重构版本对齐 PB 当前版本 `USP_PLAN_IMPLE` 硬编码，`CHANGE_TYPE` **始终为 `CK`**，不再区分 BG/CK/BQ 三种子类型。关单时按数据条件隐式区分两条处理路径。本节保留老版本语义作为历史参考，实际实现以 §11.5 和 `PB预计划plantyp10磁卡号变更业务流程分析.md` 为准。

### 3.1 变更类型语义（PB 老版本，重构已统一为 CK）

| change_type | 语义 | new_store_card | device_id | 下游单据类型 |
|---|---|---|---|---|
| `CK` | 仅磁卡号变更 | ✓ 非空 | ✗ 空 | 磁卡号变更单 |
| `BG` | 磁卡号 + 设备变更 | ✓ 非空 | ✓ 非空 | 磁卡号变更单 |
| `BQ` | 信息变更（联系人/电话/地址） | ✗ 空 | ✗ 空 | 磁卡号变更单 |

> **重构版本**：`CHANGE_TYPE` 始终 `CK`，通过 `device_id + new_store_id` 隐式区分"含设备转移/纯信息变更"两条关单路径。OP 前缀老数据 BG/BQ 仍可关单（兼容条件 `change_type in ("CK","BG","BQ")`）。

### 3.2 plantyp=10 下游 payload 构建（重构版本）

`app/services/sales_service.py:239-252` 的 `_build_downstream_payload`：

```python
elif plantyp == "10":  # 磁卡号变更（对齐 PB USP_PLAN_IMPLE 硬编码 CK）
    # PB 当前版本所有新变更单 CHANGE_TYPE 均为 'CK'，设备转移由关单时
    # 按 device_id + new_store_id 隐式判断（对齐 USP_PLAN_CONFRIM V_NEW_POSID）
    # device_id 优先取 new_posid（换设备场景），为空则回退 posid（不换设备，
    # 源磁卡号设备转移到新磁卡号下，对齐 PB V_NEW_POSID 非空分支）
    base.update(
        {
            "store_id": record.custcd or "",
            "change_type": "CK",
            "new_store_card": record.new_custcard or "",
            "new_store_id": record.new_custcd or "",
            "device_id": record.new_posid or record.posid or None,
        }
    )
```

**关单时隐式区分两条路径**（`itsm_service.py:846-857`）：
- `device_id` 非空 **且** `new_store_id` 非空 → 含设备转移：写 EidTrack type='T' + rl 转移 + 目标客户合并
- 否则 → 纯信息变更：仅同步客户主表 + 写历史 + 回写计划

### 3.3 行业通用做法

| 概念 | 字段性质 | 变更处理 |
|---|---|---|
| `cust_cd` | 业务实体ID | 全新客户才新建，终身不变 |
| `cust_card` | 物理介质标识 | 换卡时 UPDATE 字段 + 写历史表 |

**行业惯例**（银行卡换卡、会员卡补办、SIM卡换号）：同一客户实体ID不变，只更新卡号属性，写历史留痕。

**核心原则**：`cust_cd` 关联押金、合同、设备、维护记录等所有业务数据，一旦新建不可变。磁卡号变更时绝不能新建 `cust_cd`，否则所有历史关联数据断链。

| BQ 直接 UPDATE 信息字段 | `PBsrc/new_deposit.pbl/u_plan_befor_new.sru:519` | `UPDATE TMM22_CUSTOMERS SET CUSTNM=..., ADDRESS=..., PHONENO=...` |

## 5. 服务层实现

### 5.1 客户生命周期服务（`CustomerService`）

`app/services/customer_service.py`：

| 方法 | 职责 |
|---|---|
| `create_temp_customer` | 预计划创建时：新客户→TEMP，老客户保持 ACTIVE；custcd 为空时自动生成；plantyp=00 时执行磁卡号+客户名称校验 |

## 11. PB 存储过程权威逻辑还原（2026-06-26 深度调查）

> 本章基于 Oracle CCGLPDB 存储过程**真实源码**（`usp_itsm_trans_in` / `usp_trans_in_confrim` / `usp_plan_confrim` / `usp_c_tmm22`）的逐行分析，**修正**前文（第 1-10 章）中基于推断得出的若干错误结论。**本章为最高权威依据**。

### 11.1 两阶段接口架构（关键发现）

ITSM 单据完成不是"一步落地"，而是**两阶段接口**：

```
┌─ 阶段A：推送（单据关单时）────────────┐   ┌─ 阶段B：确认落地（数据接收/业务回馈）──┐
│ ITSM 关单完成                          │   │ trans.pbl/u_trans_in.sru               │
│ usp_itsm_trans_in(mid, 0, type)        │──▶│ 点"数据确认(&G)"按钮                   │
│ → INSERT sm_in_open_result             │   │ usp_trans_in_confrim(typ, id, user)    │
│   sm_in_part_change (sys_status='1')   │   │ → 老流程(XZ/GX/GH/GB/BQ/CK/BG)直接落地 │
│ 【只读 custcard，不改任何主数据】       │   │ → 新流程(00/10/20)委托 usp_plan_confrim│
└────────────────────────────────────────┘   └─────────────────────────────────────────┘
```

- **阶段A `usp_itsm_trans_in`**：纯推送，写中间接口表 `sm_in_*`，`sys_status='1'`，**不改任何客户/资产主数据**（只 SELECT `custcard`）。其 `i_type` 参数（MO/MR/MD/GB/BG/GH）只决定读哪张源表。
- **阶段B `usp_trans_in_confrim`**：人工在"数据接收(业务回馈)"界面点"数据确认"触发，才真正落地主数据。
- **新旧两套流程**：`usp_trans_in_confrim` 内 `v_tftype='00'/'10'/'20'` 时委托给 **`usp_plan_confrim`**（重构对齐的新流程）；其余字母码（XZ/GX/GH/GB/BQ/CK/BG）为旧流程。
- **PB 调用入口**：`base_objects.pbl/n_tr.sru` 声明全部 CCGL 存储过程的 RPC 接口。

#### 11.1.1 ⭐ 重构架构决策：两阶段合并为单阶段（关单即落地）

**老系统**：阶段A（关单推送到接口表）与阶段B（专人在"数据接收(业务回馈)"界面人工确认落地）是**两个分离的步骤**，需要专人事后操作"数据确认"才会触发配置/状态变更。

**新系统（已优化）**：**取消独立的人工确认环节，把阶段B的落地逻辑直接合并进单据关单逻辑**。预计划生成的下游单据执行完成（`transition` 到 `to_status="5"` 已解决/关单）时，对应客户与设备状态**立即同步变更**，无需后续专人确认。

| 维度 | 老 PB 系统 | 新重构系统 |
|---|---|---|
| 落地时机 | 关单后，专人"数据接收"确认时 | **关单完成即落地** |
| 操作角色 | 专人二次确认 | 无需，单据状态机驱动 |
| 中间接口表 `sm_in_*` | 必经 | **不再需要**（无外部 SM 系统串接） |
| 代码位置 | `usp_trans_in_confrim`/`usp_plan_confrim` | `DeviceChangeService.transition` → `_sync_customer_and_history`（`app/services/itsm_service.py:299-388`） |

**实现印证**（`app/services/itsm_service.py:314-317`）：
```python
if result.get("success"):
    # CK/BG/BQ 三种变更类型都在审核完成（to_status=5）时同步客户表并写历史
    if to_status == "5" and record.change_type in ("CK", "BG", "BQ"):
        self._sync_customer_and_history(record, operator, remark)
    db.session.commit()
```

> **结论**：本文档第 11.1 的"两阶段接口"是**老系统行为记录**；新系统已将其简化为**关单即落地的单阶段**。后续重构落地 `cust_useflg`/`useflg`/`s_status` 联动逻辑时，应统一挂在各单据 `transition(to_status="5")` 的关单钩子里，**不重建接口表与人工确认环节**。

#### 11.1.2 当前实现缺口（需补齐）

- **`StoreCloseService.transition`（`app/services/itsm_service.py:423-436`）关单时未联动客户状态**：缺少老系统 `usp_plan_confrim` 门店关闭分支的 `s_status='2'/'3'` + 名称前缀处理。
- **磁卡号变更关单未处理 `cust_useflg` → `useflg='0'`**：`_sync_customer_and_history` 仅处理 CK/BG/BQ 的 `cust_card`/信息字段，未实现移机/取机的源门店 `useflg` 失效联动。

### 11.2 客户"失效"有三个正交维度（重大修正）

前文第 1.1 节"`tmm22_customers` 无生命周期字段"的说法**错误**。老系统实际用**三个正交字段**表达客户有效性：

| 维度 | 老字段 | 取值 | 语义 | 记录是否保留 |
|---|---|---|---|---|
| **数据有效性** | `useflg` | 1有效 / 0失效 | 硬开关，逻辑删除 | ⚠️ 逻辑删除 |
| **门店经营状态** | `s_status` | 1正常 / 2临时关闭 / 3永久关闭 / 4未开通 | 经营层面停业 | ✅ 保留可追溯 |
| **客户生命周期** | （重构优化新增）`customer_status` | TEMP/PENDING/ACTIVE/INVALID | 临时→正式生命周期 | — |

**下游 SM 系统状态映射铁证**（`usp_c_tmm22`）：
```sql
decode(a.useflg, '0', 3, '1', to_number(a.s_status))
-- useflg='0' → 状态3(关闭)；否则取 s_status 的值
-- 注释：状态 1正常 2临时关闭 3关闭 4未开通
```

**结论**：`useflg='0'` 与 `s_status='3'` 在下游都映射为"关闭"，但**来源与语义完全不同**，新系统不能用单一 `customer_status` 混为一谈。

### 11.3 `cust_useflg`（客户无效化勾选）的真实逻辑

`plan_cust.cust_useflg` 复选框（"客户无效化"，on=1/off=0）的全部消费点**都在 `usp_plan_confrim`**，共 4 处：

| 业务分支 | 触发条件 | 对 `tmm22_customers` 的操作 | 目标客户 |
|---|---|---|---|
| **门店开通(00)移机** | `IF V_CUST_USEFLG='1'` | `useflg='0', pos_n=0, posstatus='03', posstatus1='31'` | `V_NEW_CUSTCD`（移出设备的源门店） |
| **旧机翻新(20)移机** | `IF V_CUST_USEFLG='1'` | `useflg='0', pos_n=0, posstatus='03', posstatus1='31'` | `V_NEW_CUSTCD`（移机源门店） |
| **取机(type=3)** | `IF V_CUST_USEFLG='1'` | `useflg='0', pos_n=0` | `v_custcd`（取机门店本身） |
| **磁卡号变更(10)** | **无条件**（不看 cust_useflg） | `useflg='0'` | `V_NEW_CUSTCD`（被换掉的源门店） |

**`cust_useflg='1'` 的本质语义**：当设备从某门店**移走/取回**后该门店已无任何设备 → 勾选则把这个**空门店**的 `useflg` 置 `'0'`（彻底数据失效），并清零 POS 台数与状态。

**重要**：该勾选**不改 `s_status`**，只改 `useflg`。它与"正式门店关闭"是两条独立路径。

### 11.4 两条"失效"路径辨析（直接回答最初疑问）

| 路径 | 触发 | 字段操作 | 适用场景 |
|---|---|---|---|
| **正式门店关闭** | 门店关闭单 → `usp_plan_confrim` 门店关闭分支 | 永久(YJ)→`s_status='3'`+`(永久关闭)`前缀；临时→`s_status='2'`+`(临时关闭)`前缀 | 门店停业但记录保留 |
| **客户无效化勾选** | 移机/取机时勾选 `cust_useflg='1'` | `useflg='0', pos_n=0, posstatus='03', posstatus1='31'` | 设备搬空后的空壳门店逻辑删除 |

### 11.5 磁卡号变更(plantyp=10)真实落地逻辑（修正第 3 章）

前文第 3.4 节"CK/BG 封装在 `usp_itsm_trans_in`"的说法**不准确**。真实逻辑在 `usp_plan_confrim` 的 `v_tftype='10'` 分支：

```sql
-- 当前门店：换新卡 + 更新名称/地址/电话，状态置正常
update tmm22_customers
   set custcard=v_custcard, custnm=v_custnm, address=v_address,
       phoneno=v_phoneno, replacedate=sysdate, s_status='1'
 where custcd = v_custcd;
-- 源门店（被移机的旧门店）：无条件失效
update tmm22_customers set useflg='0' where custcd = V_NEW_CUSTCD;
```

**修正点**：
- 磁卡号变更**支持跨门店移机换卡**：当前门店(`v_custcd`)换新卡，源门店(`V_NEW_CUSTCD`)被无条件 `useflg='0'`。
- 仅当 `V_NEW_CUSTCD` 为空（纯换卡无移机）时，才是单纯原地更新 `custcard`。
- 前文"磁卡号变更=同一 custcd 原地改卡"仅覆盖了纯换卡场景，遗漏了移机场景。

**重构版本落地**（2026-07-02 对齐）：
- `CHANGE_TYPE` 始终 `CK`（对齐 PB `USP_PLAN_IMPLE` 硬编码），不再区分 BG/CK/BQ
- `device_id = new_posid or posid or None`（兼容不换设备场景）
- 关单时按 `device_id + new_store_id` 隐式区分：
  - **含设备转移**（`device_id` 非空且 `new_store_id` 非空）：写 EidTrack type='T' + rl 转移（旧失效 `maintenancetyp='BG'`/新建）+ 目标客户 `useflg='0'` + `sflg` 保持原值不变
  - **纯信息变更**：仅同步客户主表（`custcard`/`custnm`/`address`/`phoneno`）+ 写历史 + 回写计划
- **设备 `sflg` 保持原值不变**：磁卡号变更设备从旧客户转到新客户，不经过仓库，对齐 PB `USP_PLAN_CONFRIM` 不更新 sflg
- 详见 `PB预计划plantyp10磁卡号变更业务流程分析.md` §7

### 11.6 各业务类型对客户主表的完整操作矩阵（`usp_plan_confrim`/`usp_trans_in_confrim`）

| 类型 | `tmm22_customers` 操作 |
|---|---|
| 门店开通(00/XZ) | `s_status='1', opendate=..., replacedate=null, useflg='1'`（支持二次开通） |
| 磁卡号变更(10) | 当前店换卡+信息+`s_status='1'`；源店 `useflg='0'` |
| 旧机翻新(20/GX) | `replacedate=...`；移机源店按 cust_useflg 决定 `useflg='0'` |
| 免费更换(GH) | `replacedate=..., s_status='1'` |
| 门店关闭(GB) | 永久 `s_status='3'`+前缀；临时 `s_status='2'`+前缀 |
| 门店搬迁(BQ) | `custcard=新卡, address, custnm, phoneno, contactor, s_status='1', sttransflg='0'` |
| 磁卡号变更(BG) | 只动 `tmm35_cust_pos_rl` 资产关系，不改 tmm22 状态 |
| 取机(type=3) | `replacedate=...`；按 cust_useflg 决定取机店 `useflg='0'` |

> 所有分支末尾统一调 `uf_update_cust(custcd, userid)` 同步客户（更新人/时间/开通状态/台数），并 `update plan_cust set status='01'`（完成）或 `'09'`（作废）。

### 11.7 `usp_c_tmm44` 系列存储过程定位（回答调查疑问）

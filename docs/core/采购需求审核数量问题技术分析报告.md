# 采购需求审核数量问题技术分析报告

## 一、问题描述

### 1.1 现象

在采购需求审核页面 (`PurchasePlanList.vue`)，用户修改"审核数量"后：
- 输入框失焦时，数值自动恢复为原始值
- 点击"审核通过"后，后端保存的仍是原始值，修改未生效

### 1.2 测试数据

| 申请数量 | 修改目标值 | 现象 |
|---------|-----------|------|
| 32 | 30 | ✅ 成功 |
| 2 | 3 | ❌ 失败，恢复为 2 |
| 2 | 0 | ❌ 失败，恢复为 2 |

### 1.3 初步判断

看似"响应式数据丢失"问题，多次尝试修改响应式绑定方式均无效。

---

## 二、排查过程（共 10+ 轮尝试）

### 2.1 尝试 1-3：响应式对象方案

| 方案 | 实现 | 结果 |
|-----|------|------|
| `reactive<Record<number,number>>` | `auditQtyMap[lineno] = qty` | ❌ 失焦恢复 |
| `ref<Map<number,number>>` | `auditQtyMap.value.set(lineno, qty)` | ❌ 失焦恢复 |
| `shallowRef + tick` | 普通对象 + `_tick.value++` 强制刷新 | ❌ 失焦恢复 |

**当时判断**：Vue3 响应式机制复杂，需继续尝试不同绑定方式

### 2.2 尝试 4-6：深拷贝与独立数组

| 方案 | 实现 | 结果 |
|-----|------|------|
| `ref<any[]>` + `JSON.parse(JSON.stringify)` | 深拷贝 API 数据到独立数组 | ❌ 失焦恢复 |
| `reactive<any[]>` + `splice/push` | `auditDetails.splice(0, length)` 后 push | ❌ 失焦恢复 |
| 直接修改 `auditTarget.details` | 在原始数据上加 `audit_qty` 属性 | ❌ 失焦恢复 |

**当时判断**：可能是 el-table slot 的 `row` 代理对象问题

### 2.3 尝试 7-8：绕过 slot row

| 方案 | 实现 | 结果 |
|-----|------|------|
| 按 `$index` 绑定 `formDetails[$index].rgstqty` | 新建需求页的数量绑定 | ✅ 该页面正常 |
| 按 `$index` 绑定 `auditDetailList[$index].audit_qty` | 审核页改用同样方式 | ❌ 仍有问题 |

**关键发现**：新建需求页使用 `:min="1"` 无 `:max`，而审核页有 `:max="row.rgstqty||0"`

### 2.4 最终发现

**根因**：`el-input-number` 的 `:max` 属性

```vue
<!-- 问题代码 -->
<el-input-number v-model="row.audit_qty" :max="row.rgstqty||0" />
```

当输入值 **大于** `max` 时，`el-input-number` 会在失焦时**静默回退**到 `max` 值，不产生任何错误提示。

**测试验证**：
- 申请数量 32，改 30（≤32）→ ✅ 成功
- 申请数量 2，改 3（>2）→ ❌ 被 max=2 限制回 2

## 三、根因分析

### 3.1 为什么多次尝试都失败？

```
问题层级（实际）：
  Layer 1: el-input-number :max 限制 ← 真正原因
  Layer 2: 响应式绑定方式 ← 我们关注这里
  Layer 3: slot row 代理对象 ← 次要因素

我们的排查顺序：
  尝试 1-7: 修改 Layer 2/3（reactive/ref/Map/数组/深拷贝）
  尝试 8:   发现 Layer 1（:max 限制）
```

### 3.2 诊断路径偏差的原因

| 因素 | 说明 |
|-----|------|
| 症状误导 | "失焦后恢复默认值" → 听起来像响应式丢失 |
| 组件特性隐蔽 | `el-input-number` 超出 `max` 时**静默回退**，无报错无提示 |
| 测试数据混淆 | 32→30 成功，2→3 失败 → 以为是不稳定现象 |
| 过度聚焦响应式 | 被 Vue3 响应式复杂性吸引，忽略了组件 API |

### 3.3 正确诊断 SOP

```
排查顺序（正确）：
  1. 检查组件约束属性（max/min/step/disabled/readonly）
  2. 检查事件绑定（v-model vs :model-value + @update）
  3. 检查数据响应式（ref/reactive/代理）
  4. 检查数据流（父子组件、API、共享引用）

本次顺序（错误）：
  直接从第 3 步开始，跳过了第 1 步
```

## 四、解决方案

### 4.1 最终方案

**去掉 `:max` 限制，改用自定义校验：**

```vue
<template>
  <el-input-number 
    :model-value="auditDetailList[$index].audit_qty"
    @update:model-value="(v) => setAuditQty($index, v)"
    :min="1"
  />
</template>

<script>
function setAuditQty(index: number, val: number | null) {
  const row = auditDetailList[index]
  const qty = Number(val) || 0
  
  if (qty < 1) {
    ElMessage.warning('审核数量必须大于0')
    row.audit_qty = 1  // 明确回填
    return
  }
  
  // 允许大于申请数量（业务规则）
  row.audit_qty = qty
}
</script>
```

### 4.2 数据结构优化

```typescript
// 使用 reactive 数组 + 展开运算符创建独立副本
const auditDetailList = reactive<any[]>([])

function openAudit(row: ProcRecord) {
  auditDetailList.splice(0, auditDetailList.length)
  for (const d of row.details) {
    // 关键：展开运算符创建新对象，Vue 会响应式代理
    auditDetailList.push({ ...d, audit_qty: Number(d.rgstqty) || 0 })
  }
}
```

### 4.3 业务规则明确

| 规则 | 说明 |
|-----|------|
| 审核数量 ≥ 1 | 最小值限制，=0 时提示并回填为 1 |
| 允许大于申请数量 | 业务允许超量审核（后续可能加提示确认） |
| 提交前校验 | `auditqty < 1` 时禁止提交 |

## 五、经验教训

### 5.1 调试经验

1. **组件 API 优先于框架原理**
   - 不要一上来就怀疑 Vue 响应式
   - 先检查组件的 props（max/min/disabled 等）

2. **静默行为的危害**
   - Element Plus 的 `el-input-number` 超出范围时静默回退
   - 类似：`el-select` 的 `filterable` 匹配不到时自动清空
   - 这类行为需要显式处理，给用户提供反馈

3. **测试数据要全面**
   - 不要只用一种数据测试
   - 应测试：边界值、超界值、空值、负值

### 5.2 代码规范建议

```vue
<!-- 不推荐：默默限制 -->
<el-input-number v-model="qty" :max="maxQty" />

<!-- 推荐：显式控制 -->
<el-input-number 
  :model-value="qty" 
  @update:model-value="handleQtyChange"
/>

<script>
function handleQtyChange(val: number | null) {
  const num = Number(val) || 0
  if (num > maxQty) {
    ElMessage.warning(`数量不能超过 ${maxQty}`)
    qty.value = maxQty
    return
  }
  qty.value = num
}
</script>
```

### 5.3 时间成本

| 阶段 | 耗时 | 产出 |
|-----|------|------|
| 响应式方案尝试 | ~2小时 | 10+ 种方案均失败 |
| 发现 max 限制 | 5分钟 | 定位真正原因 |
| 实施最终方案 | 30分钟 | 稳定可靠 |

**结论**：前期诊断方向错误导致大量无效工作，后期通过对比"成功页面"和"失败页面"的差异快速定位。

API 设计：双端点 vs 统一端点

文档设计了两个独立端点，但底层操作本质相同——都是"从需求行创建订单+写TPC20关联"

文档方案：两个专用端点

POST /orders/batch — 拆单专用
└─ 输入：多个订单，每个有各自的 suppliercd + details
└─ 循环调用 create()，写 TPC20

POST /orders/merge-create — 并单专用
└─ 输入：按 itemcd 分组的 merge_groups
└─ 每组生成一个订单，写多条 TPC20

⚠️ 两套入参格式，两套校验逻辑，两套前端调用

替代方案：统一端点

POST /orders/batch — 同时支持拆单和并单

输入格式完全不变（文档已有）：
{ "orders": [{ "suppliercd": "...", "details": [...] }] }

└─ 拆单：同一个 ref_pcplanid/ref_pclineno 出现在不同 order 里 → 自动拆
└─ 并单：不同 ref_pcplanid 出现在同一个 order 里 → 自动并
└─ 校验逻辑统一：汇总所有 ref 的 qty vs available_qty

✅ 合并预览接口保留，但最终执行都走同一个 batch 端点
A

保持文档方案：双端点

拆单和并单各有独立端点，语义明确，入参针对各自场景优化

优点

  • 每个端点职责单一
  • 前端调用意图清晰
  • 独立演进不互相影响

缺点

  • 后端重复代码多
  • 两套参数校验
  • 并单预览→执行的参数要转换
B

统一端点 + 保留预览

只保留 /orders/batch，拆单/并单走同一个执行路径。保留 /requisitions/merge-preview 做智能分组

优点

  • 一套校验逻辑，减少 bug
  • 自动支持组合场景
  • 代码量减少约40%

缺点

  • 入参结构较通用
  • 前端需自行组织 orders 数组

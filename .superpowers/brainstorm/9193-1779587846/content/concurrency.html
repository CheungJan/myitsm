并发控制方案

防止两个用户同时下单导致同一需求行的订购量超过可用余额

问题场景

需求行 PP000180-行1：电源 × 100，已有订购50，可用余额 = 50

用户A：准备下单 40个 → 读取 available_qty=50 ✓
用户B：准备下单 30个 → 读取 available_qty=50 ✓
两个都通过校验 → 总共下单70个 → 超出可用余额20个 ❌

方案：SELECT ... FOR UPDATE 行级锁

核心思路：不锁需求行本身（需求行在 TPC02 表中是只读的），而是在写入 TPC20 关联表之前，对已存在的关联记录加锁，确保同一需求行的并发写入串行化。 
# 在 batch_create 事务中
SELECT COALESCE(SUM(linkqty), 0)
FROM tpc20_requisition_order_link
WHERE pcplanid = :pid AND pclineno = :lno
FOR UPDATE;   ← 行级锁，阻塞其他并发事务

# 然后检查
if already_linked + new_qty > auditqty:
    raise ValueError("超出可用余额")

# 通过后写入 TPC20 + 订单
INSERT INTO tpc20_requisition_order_link ...
COMMIT;  ← 释放锁
A

FOR UPDATE（推荐）

利用 PostgreSQL 行级锁，事务内串行化同一需求行的写入

优点

  • 数据库原生保证，无竞态
  • 锁粒度小（仅锁需求行）
  • 实现简单，无需额外组件

缺点

  • 并发高时可能有等待
  • 需注意事务超时设置
B

乐观锁（版本号）

TPC02 需求行加 version 字段，更新时检查版本

优点

  • 无锁等待
  • 适合读多写少

缺点

  • 需改 TPC02 表结构
  • 失败需重试逻辑
  • 改动范围大
